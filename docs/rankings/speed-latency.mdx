   - **批量截图归档批次**：`speedtest-2026-08-11-cst`（2026 年 8 月 11 日 Asia/Shanghai 时区），共完整留存 **16 张原尺寸 1122×1402 PNG 原始测速图**（其中 15 家已入驻本库 42 家榜单，另有「快狸」同步归档作比对样本），叠加品牌库额外收录的 **[微风网络](/docs/brands/weifeng)** 与 **[无忧链接](/docs/brands/wuyou)** 实测截图，总计构成 **17 家库内品牌图证体系**。
   - **主要测试后端**：绝大多数图像由 `MAI-TEST-BOT 2.0.0-dev` 在 **珠海联通 5Gbps 后端、32 线程并发、5 次 ICMP/TCP Ping** 条件下采集；[宇宙云](/docs/brands/yuzhou) 与「快狸」采用 `主端 4.3.3 (696) / 喵速 4.7.0 (A11-32)`（珠海联通 9Gbps、32 线程、TLS RTT + HTTPS 延迟）进行采样。
2. **必须声明的数据局限性 (Limitations)**：
   - **单日非同时刻快照**：16 张批次截图拍摄于 `2026-08-11` 全天不同时段（涵盖凌晨 `00:21`、白天 `14:32`、晚高峰 `18:45 - 22:46`），并非同一毫秒的受控对比。因此，**本榜不宣称某一品牌“永远最快”，也不以单张测速图替代长期稳定性结论**。
   - **真实缺陷保留原则**：实验室严禁裁剪或涂改截图中的 `0B` 失效节点、`KB` 级慢速节点、异常高延迟及 `UDP Unknown / RestrictedCone` 结果——这些异常指标恰恰是评估机场整体运维健康度的核心依据。

## 四、晚高峰 StDev 抖动、丢包率与 4K/8K 实感解码深度剖析

看懂一张 `MAI-TEST-BOT` 或 `喵速` 测速图，绝不能只盯着最右侧的最大值（Max Speed）看！实验室教你用专业网络工程师的视角拆解图中的三大隐性指标：

### 1. 标准差抖动（Jitter / StDev）与速率曲线形态
- **平滑饱满型曲线（优秀）**：在测速图的右侧速度曲线缩略图中，如果曲线呈快速爬坡后平稳拉直的高台形状（例如光速云、微风网络、U1S1 的香港 IEPL/IPLC 节点），说明传输通道的 **拥塞窗口稳定、物理专线无明显丢包重传**。观看 YouTube 4K 60FPS 时，缓冲进度条会快速甩开播放点 30~60 秒。
- **锯齿剧烈震荡型曲线（亚健康）**：如果平均速度只有 80Mbps，但最高速度标到 450Mbps，曲线呈现剧烈的“尖峰—归零—再尖峰”锯齿形态，通常意味着后端出现了 **短时突发限速（Token Bucket Shaping）或严重的跨网丢包重传**。这种节点虽然测速峰值好看，但实际打游戏会人物瞬移、看直播会周期性卡顿。

### 2. 日美跨洋节点真实吞吐落差解读
细心的读者会发现一个普遍规律：在光速云、暮光加速、飞猫云、二猫云的实测数据中，**香港/新加坡节点普遍跑出 380Mbps~548Mbps，但日本节点往往在 130Mbps~150Mbps，而美国洛杉矶节点单次测试仅在 14Mbps~19Mbps（注：CyberGuard、WgetCloud 等特定优化美日线路除外）**。这是为什么？
- **BDP（带宽延迟积）与单流窗口物理规律**：香港 RTT 约 22ms，TCP ACK 确认包每 0.022 秒就能往返一次；而美西 RTT 高达 143ms~178ms，是香港的 7 倍以上！在相同的单连接 TCP 缓冲区窗口限制和短时测速窗口（通常只有 5~10 秒）内，跨太平洋链路还没来得及把 TCP 慢启动（Slow Start）窗口拉满，测速就已经结束了。
- **真实 4K 体验**：YouTube 4K 60FPS 真实码率仅需 **25Mbps~40Mbps**，1080P 仅需 **5Mbps~8Mbps**。因此，日本 `135Mbps` 足以轻松秒开 4K 甚至 8K，而美国节点只要 **丢包率为 0% 且曲线平稳**，看 4K 视频或使用 ChatGPT（纯文本吞吐仅需几十 KB/s）同样丝滑无卡顿。

### 3. 异常节点（0B / 超高延迟）与 UDP NAT 类型透视
- **为什么图里偶尔会有个别 `0B` 节点？**  
  在整组订阅批量自动化测速时，服务商可能正好在对该冷门地区节点进行重启维护、更换落地 IP，或者测速瞬间该节点触发了后端的临时连接数保护，因此出现单次 `0B` 是全行业常见现象（也是实验室诚实保留原图不删改的原因）。判断机场是否健康，要看 **主力区域（香港/新加坡/日本/美国）的核心节点群可用率是否高于 90%**。
- **UDP NAT 类型（FullCone vs RestrictedCone vs Unknown）**：  
  - 图中显示 `FullCone`（全锥型 NAT）的节点，**对于联机电竞游戏（Switch/PS5/APEX/Valorant）和语音通话极其友好**，能顺利完成 P2P 打洞降低联机掉线率；
  - 显示 `RestrictedCone` 或 `Symmetric` 属于受限型，对网页浏览、看视频和 AI 对话没有任何负面影响；
  - 若节点大面积出现 `UDP Unknown`，则说明该节点可能屏蔽了 UDP 转发（或底层仅开启 TCP 转发），游戏玩家需避开此类节点，改选支持 FullCone 的专线节点。

## 七、测速与延迟性能常见 FAQ (10 问)

### Q1：为什么香港测速有的 21ms、22ms，有的却 45ms 甚至 151ms？物理极限是多少？
**答**：从中国深圳或广州出发穿过深港边界抵达香港数据中心，光纤中光速折射后的物理往返最低极限通常在 **6ms ~ 12ms** 之间；加上用户在省内接入城域网、国内入口转发及协议加解密的耗时，华南用户连香港专线正常在 **15ms ~ 25ms**，华东/华北用户在 **35ms ~ 55ms**。如果在同一测试端测出香港高达 150ms（如部分海外中转节点），通常是因为流量先绕去了第三地（如日本、美国或新加坡）再折返香港，或者走了极度拥堵的普通公网线路。

### Q2：为什么有些机场宣传“2000Mbps / 6Gbps 带宽”，实际测速只看到 450~548Mbps？
**答**：因为测速结果同时受限于 **测试机本地物理网卡、单次突发并发限制与节点共享调度策略**。500Mbps（约合 62.5MB/s 的实际下载速度）已经远超普通用户观看 8K 视频（约 80~120Mbps）的需求上限；运营商标称的 2000Mbps 或 6Gbps 通常指的是该机场服务器集群的 **总出口接入池容量**，而非单个客户端单线程无上限抢占全部带宽。

### Q3：为什么我的手机测速只有 80Mbps，和电脑端测出来的 400Mbps 差这么多？
**答**：影响测速上限的不仅是机场，还有 **本地终端设备 CPU 算力与 Wi-Fi 吞吐**。老旧手机或入门路由器在处理高强度加密协议时单核 CPU 容易吃满形成瓶颈；此外，2.4GHz Wi-Fi、隔墙后的 5GHz 信号衰减以及部分客户端后台开启了分流规则匹配都会明显拉低测速峰值。建议统一使用网线直连电脑并关闭不必要的后台下载后测试。

### Q4：测速截图里的 `Shadowsocks` 和后台的 `VLESS / IEPL` 冲突吗？
**答**：不冲突。很多同时支持多协议的机场（例如光速云、飞猫云、SOGO 云、一翻云）会在后端同时下发多种协议格式的节点分组，或者订阅链接根据请求端 User-Agent 自动返回对应协议配置文件。`speedtest-2026-08-11-cst` 批次中，使用 `MAI-TEST-BOT` 的 14 家机场当时拉取了对应的 Shadowsocks 订阅组进行统一压测，而使用 `喵速` 的宇宙云则拉取了 VLESS 组进行测试。

### Q5：测速跑得快，是不是就一定能解锁 Netflix 和 ChatGPT？
**答**：**完全不是一回事！** 测速测试的是“入口到落地服务器之间的传输管道有多宽、延迟有多低”；而 Netflix 版权解锁和 ChatGPT/Claude 防风控测试的是“落地服务器的出口 IP 在全球风控数据库里的信誉度与归属地”。因此，我们在 [README 测速规范] 中也反复强调：测速截图只能证明该时刻的延迟与带宽，AI 与流媒体解锁能力必须查看各品牌详评页中的独立核验记录。

### Q6：测速图里看到某个节点显示 `Timeout` 或 `0B`，这家机场是不是就不能买了？
**答**：不能一刀切。批量并发扫全订阅几十个节点时，往往包含一些冷门测试节点或正在维护轮换的备用线路，出现 1~2 个 `0B` 属于运维常态。真正危险的信号是 **超过 30% 的主力地区（香港/日本/新加坡/美国）同时出现 `0B` 或延迟全部飙升到 300ms 以上**，那说明该机场后端机房出现了大面积过载或遭遇封锁。

### Q7：我在上海/北京，用珠海测速图作为参考准确吗？
**答**：绝对数值会有地域差异，但 **横向梯队参考价值极高**。由于北京/上海距离深港专线入口比珠海远了约 1000~2000 公里，北方用户直连深港入口的绝对延迟通常会比珠海实测图多出 **18ms ~ 35ms**（例如珠海测香港 22ms，上海约 38~42ms，北京约 48~55ms）；但在 **沪日专线（上海至东京）** 方向上，上海用户的实测延迟反而会比珠海更低（往往只有 28~35ms）。

### Q8：什么是“晚高峰黄金窗口”？为什么非要在晚上 8 点到 11 点测速？
**答**：工作日的 **20:00 - 22:30（部分地区延至 23:00）** 是全社会家庭宽带娱乐、高清视频流与游戏流量同时爆发的峰值时段。此时公网国际出口负载率接近 100%，劣质直连机场和过度超售的共享中转会在这个时间段原形毕露（延迟翻倍、疯狂丢包）。如果一家机场在 21:00 左右依然能维持 350Mbps+ 吞吐和低延迟（如本次批次中 `21:04` 的宇宙云、`22:33` 的 U1S1、`22:46` 的极连云），其底层冗余度就经受住了最严苛的实战考验。

### Q9：可信云测速图的日期在底部没显示全，数据还真实吗？
**答**：真实有效。在 `speedtest-manifest.json` 数据清单中，实验室对可信云进行了严谨的数据透明标识：图像中可见精确测试时间为 `15:32:35 CST`，其物理文件归属于 `2026-08-11` 同批次压缩包，因此标注为 `date-inferred-from-batch-time-visible-in-image`（由同批压缩包时间推断日期）。绝不隐瞒任何边缘瑕疵，正是网络可观测实验室维持客观公信力的底线。

### Q10：如果不满足于测速图，我自己怎么用客户端测试“真·Goodput”而不是假测速？
**答**：不要只看机场自带测速功能或访问被商家加白的 `speedtest.net`。最简单真实的验证方法有两个：一是晚上 21:00 打开 YouTube 找一段 **4K 60FPS 视频**，右键开启“详细统计信息（Stats for nerds）”，看其中的 `Connection Speed` 是否能稳稳突破 `80,000 Kbps` 且 `Buffer Health` 迅速积累到 30 秒以上；二是在命令行直接从 GitHub Releases 或 HuggingFace 拉取一个 500MB 以上的模型/安装包，观察实际下载字节速率是否稳定不掉速。
